# Archive-scale triage performance and the SSH terminal stack

The existing engine read a 7.13 GB ZIP in 57.5 seconds under a 512 MB setting. Scoring the archive and writing reusable results took about eight minutes. Those are reasonable costs for preparing an investigation. Repeating either job when the analyst switches from “A and B” to “A without B” would make the workbench difficult to use. The `triager` design keeps membership and selected fields on disk so subsequent drill-downs can read the prepared results. [Archive benchmark records](../.kiro/specs/npu-log-decision/tasks.md#implementation-notes) · [Venn drill-down recipe](../.kiro/specs/triager/recipe.md)

## What the workstation measured

The AIT runs used the same all-entry scope from `russellmitchell.zip`. The reader saw 30,916,764 records across 11,870 entries, skipped 357,123 records, and retained 30,559,641 occurrences of 8,276,854 distinct originals. The historical timings cover complete release commands. The records do not establish the operating system's file-cache state. [Measurements for tasks 1.17 and 1.20](../.kiro/specs/npu-log-decision/tasks.md#implementation-notes)

| Operation | Elapsed | Throughput and memory |
|---|---:|---|
| Ingest all entries and deduplicate with disk spill | 57.5 s | About 538,000 input records/s. Counted heap peaked at 374.4 MiB and process working set at 379.3 MiB. |
| Score all distinct originals and write result parts | 487.8 s | About 17,000 distinct originals/s including I/O. Counted heap peaked at 355.0 MiB and working set at 359.1 MiB. The score and occurrence tables had identical logical hashes in the in-memory and spilled runs. |
| Run the actual NPU/Venn policy on 96 CSIC queries against 64 history records | 91.8 s | 6,240 encodes, with 89.2 s in encoding. The run recorded 1.15 GiB of counted reservations under a 2 GiB limit. Native provider peak memory was unmeasured. |
| Verify those decisions by rerunning the policy | 119.4 s | Another 6,240 encodes, with 116.3 s in encoding. Every score, decision and allocation agreed. |

In the policy run, each query required its own encoding and 64 history encodings. That makes 6,240 encoding calls for 96 decisions. A separate batched encoder test reached 2,037–2,166 logs/s after warm-up. The product path uses one original per fixed-shape NPU image. Use the policy timing when estimating a similar hunt, and record both query count and encoding count. The retained `policy-status.json`, `replay-status.json` and matching stdout receipts are under `policy-cli-fmy7e_ck` in the comparison's run directory. ## What the new workbench must demonstrate

The first Rust workbench can reopen a bounded policy report. On the 96-original CSIC development report, `l2d --json tui --report … --session …` recovered all 35 originals in the saved recommendation region. Its memory budget recorded a peak of 49,395,456 bytes (47.1 MiB) for that process. This measures counted reservations, including the process baseline. The PTY test reproduced the ordered membership digest from the parent decisions. Archive-scale latency, resident memory and real SSH redraw time remain measurements for the gates below. [Retained-report end-to-end case](qualification/triager-e2e.md)

| Analyst action | Measurement and proposed acceptance |
|---|---|
| Open an archive and build A and B | Record compressed and inflated bytes, accepted occurrences, distinct originals, elapsed time, heap and process peaks, and spill bytes. Reconcile exact counts and ordered IDs across batch sizes and forced spill. Run the archive path at 512 MB. A scoped NPU run gets its own admitted budget because its session alone reserves 1 GiB. |
| Narrow a Venn region | Record parent, included, excluded and unknown counts in both originals and occurrences. Show the retained share and the population C actually assessed. These measures reveal whether the system saved model work or silently lost coverage. |
| Reopen, page or facet a prepared region | On the reference host, measure first-page and drill-down p50/p95 over at least 30 interactions. The proposed target is p95 at most 2 s for an indexed 25-row page or prepared aggregate, with zero archive rescans, reinflations, repeated scoring, NPU calls or GenAI calls. |
| Resize the sidebar or search editor over SSH | Retain the same query, cursor and evidence receipt. Time input-to-visible redraw separately from backend page fetch. Record terminal size, SSH round-trip time and bytes written. A resize consumes zero analytical work. |

These are acceptance measures for the planned MCP service and terminal. The two-second target and SSH responsiveness still need a run on the new implementation. For each cold run record which artifacts already existed. For a warm run identify which indexes and projections were reopened. ## Terminal research and stack decision

The selected SSH stack is **Taffy for pane layout, Ratatui for widgets and cell rendering, and Crossterm for keyboard, mouse and resize events**. The sidebar width and search editor height are local UI state. Taffy calculates pane rectangles in terminal-cell units and Ratatui renders the results into them. The published `ratatui-flex` 0.0.0 crate reserves a name and exposes no API. Ratatui documents Taffy integration examples, and the separate `panes-ratatui` adapter is a candidate for converting rectangles. The adapter choice can be tested on the workbench layout. [Taffy](https://docs.rs/taffy/latest/taffy/) · [Ratatui layout integrations](https://ratatui.rs/concepts/layout/#other-layout-approaches) · [Ratatui backends](https://ratatui.rs/concepts/backends/) · [Reserved crate](https://docs.rs/ratatui-flex/latest/ratatui_flex/) · [Pane adapter](https://github.com/jostled-org/panes)

**Dioxus deprecated its original public TUI renderer.** In September 2026 Dioxus Labs reported that Devin CLI uses a rebuilt Dioxus terminal renderer. That announcement describes a shipping application and gives no public replacement SDK or support commitment. A separate community project also provides a Blitz-based terminal renderer. Taffy can be used independently of any of these renderers. Ink remains a React/Node alternative for a team that wants to build its terminal client in TypeScript. [Dioxus renderer status](https://dioxuslabs.com/learn/0.7/beyond/project_structure/) · [Dioxus Labs announcement](https://dioxuslabs.com/blog/joining-cognition/) · [Community renderer](https://github.com/JakkuSakura/dioxus-tui) · [Taffy project](https://github.com/DioxusLabs/taffy) · [Ink](https://github.com/vadimdemedes/ink)

The Tauri analogy fits the separation of responsibilities. A Tauri desktop app can keep its engine in Rust and display a web frontend through the operating system's WebView. Here the same Rust investigation service feeds a terminal-cell frontend over SSH and a separate MCP adapter. A future desktop client could reuse the service and its evidence receipts. Its screen implementation would be specific to the WebView. [Tauri process model](https://v2.tauri.app/concept/process-model/) · [Shared service design](../.kiro/specs/triager/design.md)
